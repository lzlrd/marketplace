# Security guidance

Repo-wide security policy for the `lzlrd` marketplace and the plugins it ships. It is codebase-specific: the committed file that the security-guidance plugin's diff review and the 4man Reviewer read before reviewing a change here.

## Scope

The marketplace vendors the plugins listed in `.claude-plugin/marketplace.json` (all as in-repo source) — that manifest is the roster; don't restate it here. The ones with a real security surface: two MCP servers that run code on Bun (`realfavicon-mcp`, `offshore`), one plugin that registers shell hooks and ships two commands that edit the user's CLAUDE.md (`mempalace-hooks`), one that ships local Python scripts (`export-skills`), and one whose skill pre-approves a bundled shell script and adopts instruction files (`reload-claude-md`). The rest are skills and command/agent definitions with no runtime of their own, apart from `prompting`'s maintainer script `scripts/sync-references.sh`: when a maintainer runs it, it downloads vendor pages and overwrites the skill's references, which the model then reads as guidance, so review its output like any other change to instructions. The sections below cover the parts that matter.

## realfavicon-mcp

Every argument of every tool arrives from an MCP client (often LLM-driven) and is untrusted: all of `realfavicon_generate`'s (`source`, `dark_icon_source`, `output_dir`, `path`, `version`, `app_title`, `app_name`, `short_name`, `theme_color`, `background_color`), `url` and `include_icon_data` (`realfavicon_check`), and `since` and `format` (`realfavicon_changelog`). Validate at the boundary with each tool's zod `inputSchema` (hex colours are regex-checked, `url` is `z.string().url()`, `path` and `version` refuse `"`, `<` and `>`). Do not loosen these. Every handler wraps its body in try/catch and returns `{ isError: true }` rather than throwing out of the process.

`realfavicon_generate` and `realfavicon_check` issue outbound `fetch` on caller-supplied URLs, and `realfavicon_check` also fetches the icon and manifest URLs named by the page it fetched, so server-side request forgery is inherent to the tool's purpose. `realfavicon_changelog` fetches one fixed URL; the caller supplies only `format`. Contain it:

- Every request to a caller-supplied or page-supplied URL goes through `safeFetch` in `src/net.ts`: the page fetch and the checker's fetcher in `check.ts`, and both downloads in `generate.ts`. It requests with `redirect: 'manual'` and runs `assertSafeFetchUrl` on the first URL and on every redirect target, up to 5 hops. Never call bare `fetch` on such a URL, never hand the check library its default fetcher, and do not add scheme-relaxing or redirect-following to `file://` and similar.
- `assertSafeFetchUrl` resolves the host and refuses link-local / cloud-metadata addresses: 169.254.0.0/16, fe80::/10, fd00:ec2::254 (AWS), fd20:ce::254 (Google Cloud), fd00:c1::a9fe:a9fe (Oracle Cloud), 100.100.100.200 (Alibaba Cloud), and the same IPv4 addresses written as IPv4-mapped (`::ffff:`), NAT64 (`64:ff9b::/96`) or 6to4 (`2002::/16`) IPv6. A network-specific NAT64 prefix (such as `64:ff9b:1::/48`) is not unwrapped, because the address does not say where the IPv4 bits sit. Loopback and private LAN are intentionally allowed so localhost/intranet dev servers still work; that also lets a fetched page point the checker at another loopback or LAN host, which is accepted for a local stdio server. The guard resolves the name and `fetch` resolves it again, so DNS rebinding is not covered. If you add a new outbound fetch, send it through `safeFetch`.
- `realfavicon_check` bounds every request: 30 s for the page, 10 s for each icon or manifest (body included), 60 s for the whole check. `safeFetch` races the guard's DNS lookup against the same signal, so name resolution counts toward those limits. Keep the body read inside the fetcher, under the signal.
- Icons, the manifest and a downloaded master image are typed by their first bytes (`src/sniff.ts`, which decodes at most the first 64 KiB, with patterns that run in linear time), and an HTML or empty body is refused. Only bytes `sniff` does not recognise fall back to the `Content-Type` and then to the URL extension, which becomes the image type in `favicon.svg`. The checked page itself is accepted only when its `Content-Type` is `text/html`, `application/xhtml+xml`, or absent. A label is caller-controlled, so never let it override what the bytes say.
- Do not echo internal response headers or bodies beyond what each tool contract returns.
- This server runs locally with the invoking user's privileges, not as a hosted multi-tenant service. If it is ever exposed as a network service, tighten the guard to also block private ranges before shipping.

On the filesystem: `realfavicon_generate` writes to the caller-supplied `output_dir`, but the filenames come from the RFG library (a fixed set: `favicon-96x96.png`, `favicon.ico`, `favicon.svg`, `apple-touch-icon.png`, `site.webmanifest`, `web-app-manifest-192x192.png`, `web-app-manifest-512x512.png`), not from caller input, so there is no filename-driven path traversal. If any of those names in `output_dir` is a symlink, the call is refused before anything is written, and each file is opened with `O_NOFOLLOW`: a cloned repository's public folder can carry such a link. Keep both. Temp downloads use `tmpdir()` plus `crypto.randomUUID()` and are unlinked in a `finally` on both success and error. Keep the cleanup; never write temp files to predictable paths. Relative `source`, `dark_icon_source` and `output_dir` resolve against `CLAUDE_PROJECT_DIR` and are refused when it is unset or not absolute; never resolve them against the working directory, which is the plugin's install directory under the launch command. The tool replaces existing files of the generated names and lists them in `overwritten`; if a later write fails, the error text names the files already written and which of them replaced existing ones. It is annotated `destructiveHint: true`. `app_title` is HTML-escaped before it reaches the returned markup. An SVG master is copied into `favicon.svg` unsanitised, scripts included.

The server needs no API keys (the RFG npm libraries and the change-log endpoint are unauthenticated). Do not add credential handling, and never log request URLs or bodies that could carry user data.

## offshore

Offshore forwards prompts to an uncensored model on purpose. That filter bypass is the tool's stated function and the user's own choice. Keep it a tool run locally with the user's privileges, never a hosted multi-tenant service. The endpoint is whatever a provider's `base_url` names, local or remote. Credentials come from the environment (`env_key` per provider, `OFFSHORE_API_KEY`, `env_http_headers`) or from `config.toml` (`http_headers`, `query_params`, and userinfo in `base_url`). Never log a request URL, or put one in a tool or error result, with its userinfo or query string: reduce it to origin and path. Never log request bodies, headers or keys.

## mempalace-hooks

All three hooks (SessionStart, UserPromptSubmit, PostToolUse) run `set -uo pipefail`, always exit 0, and emit at most one fixed directive each (plain text, or for PostToolUse a JSON object built from a constant string), so a hook failure cannot break a session (fail-open). `session_id` feeds marker and `rm` paths, so it is stripped to `[A-Za-z0-9_-]` before use to block `../` traversal. The hooks read and write only their own state directory and inject text; they never execute model output. That directory lives under `XDG_STATE_HOME` or `HOME`, each used only when it is an absolute path, and is created with mode 700: never fall back to a shared directory such as `/tmp` or to a path relative to the user's project, and never write a marker through a symlink. With no usable state directory, or a diary marker that exists but cannot be read, the PostToolUse nudge stays silent rather than fire on every edit; the UserPromptSubmit style reminder then has no cooldown and repeats on each matching prompt, and SessionStart cleans nothing up. The hook commands in `hooks/hooks.json` quote `${CLAUDE_PLUGIN_ROOT}`; keep the quotes. On Claude Code 2.1.319 the root reaches the hook as an environment variable, so an install path with `$` or a backtick in it runs as is there; the plugins reference also describes the placeholder as text substitution, under which those two characters would break the command.

`/mempalace-hooks:setup` and `/mempalace-hooks:uninstall` are user-invoked only (`disable-model-invocation: true`) and pre-approve only their own script with a fixed scope argument. Never grant them bare `Bash`. `setup.sh` and `uninstall.sh` change a user's CLAUDE.md only through `setup/block.py`, loaded from the scripts' own directory (never from an inherited `CLAUDE_PLUGIN_ROOT`). It splits the file on line feeds only, counts a marker only as a whole line, and pairs markers in order. It refuses to write when a marker is unpaired, when a whole-line marker sits inside a code fence (fences are counted from line 1), or, on inject, when the file ends inside an unclosed fence. Keep all three refusals, since a pattern matched across the file can delete the user's own text. It writes through a CLAUDE.md symlink only to an existing `.md` file, so a cloned repository's CLAUDE.md that links to a shell startup file is refused, and it creates each backup with `O_CREAT|O_EXCL|O_NOFOLLOW`, mode 600, so a link planted at a backup name is never followed. `bash mempalace-hooks/tst/run.sh` covers these cases; run it after any change to the hooks, the commands or the setup scripts.

## export-skills

Two standard-library Python scripts and their shared module `skill_rules.py`, which holds the frontmatter reader and the name and upload rules. The skill runs them locally with the user's privileges. They make no network request and execute nothing they read. `inventory.py` only reads, under `CLAUDE_CONFIG_DIR` when it is set and `~/.claude` otherwise: the plugin cache, `installed_plugins.json`, `known_marketplaces.json` and each marketplace's `marketplace.json` (including at an `installLocation` that file names), `enabledPlugins` in the settings files, and the personal skill directories; and Claude Desktop's config and extension list. The skill keeps its work files, the inventory included, in a private temporary directory or in `--out`, never at a fixed path in `/tmp`.

`package.py` reads a manifest the model wrote, so every field is untrusted: an entry's `name` becomes a zip folder and file name only after it has matched `[a-z0-9-]+` and the skill's own frontmatter name, a zip name with a path separator is refused, and nothing is written for an entry with any issue. Keep those checks ahead of every write. In `--out`, a folder the caller chose and possibly a cloned repository's, it writes only through temp files it creates exclusively (random name, never an existing path or a symlink) and renames into place. It deletes or replaces a file there only when its index (`.export-skills-index.json`) names it as a plain `*.zip` base name it wrote, or when the zip it is about to write already exists and holds only that skill's folder with `SKILL.md` at its root (an export from a version without the index). Never widen either rule to a glob.

What goes into a zip: a root file ships only when `SKILL.md` names it from the skill root (bare, after `./` or after `${CLAUDE_SKILL_DIR}/`). A left-out directory ships when `SKILL.md` or a shipped Markdown file names a path inside it, from the skill root or relative to that file's own folder (`../` included), but never when the name follows another path such as `~/.claude/`. A dot directory, or one named `secrets` or `credentials`, never ships at any depth, mentioned or not. Files on the `CREDENTIAL_FILES` list never go into a zip, and the advisory `SECRET_RE` warning does not replace that list: extend the list, do not relax it. Both rules apply to a symlinked member's own name and to what it resolves to (a file's name and parent directory, a directory's name), so `scripts/helper -> ~/.ssh/id_ed25519` stays out. Beyond that, a symlink is followed only when it resolves inside the skill's own folder; one that leads anywhere else is left out and listed, since an ordinary name such as `hosts.yml` can hold a token. Keep that boundary, the loop check and `WALK_CAP`. The rules go by name, not content. The tests in `tst/` run both scripts against a temporary `HOME` with `CLAUDE_CONFIG_DIR` cleared or set to a temporary directory; do not add a test that reads the real `~/.claude`.

## reload-claude-md

The skill re-reads instruction files and adopts them as authoritative, so what it pre-approves is its security boundary. Its `allowed-tools` grants two things only: running the bundled `skills/reload-claude-md/scripts/discover.sh` as `bash "${CLAUDE_SKILL_DIR}/scripts/discover.sh"` or the same command unquoted, each an exact command with no wildcard, and reads of files named `CLAUDE.md` or `CLAUDE.local.md`. Do not widen either to bare `Bash` or `Read`, and keep `disable-model-invocation: true` so that only the user can start it. `discover.sh` takes no arguments, reads no memory file and writes nothing. Besides `find` and `realpath` it runs only `git rev-parse --show-toplevel --git-common-dir` in the working directory, and it prints paths. Any other read goes through the user's own permission rules: an import outside the working directory, and a `CLAUDE.md` that links to a file with another name. Settings files can hold credentials in their `env` block, so the skill never opens one with Read: it searches each with the Grep tool for the `claudeMdExcludes` key alone. When a file's exclusions cannot be learned, it does not adopt a file that has no copy in context. A nested `CLAUDE.md` that the session never loaded is otherwise still adopted on reload; that is a deliberate choice, so do not rely on discovery to keep third-party copies out. `tst/run.sh` pins the grant and the script's output: a change to either should fail it first.

## General

- The stdio transport owns stdout on both MCP servers. Never write non-protocol output to stdout (`console.log`); it corrupts the JSON-RPC stream. Diagnostics go to stderr only.
- Validate every MCP tool input at the boundary with its zod schema.
- No `eval`, no shell execution of caller-controlled input, no dynamic `import()` of caller-controlled paths.
- A command a skill or command file tells the model to run must not delete a path computed at run time (`rm` of a variable or of `$(git rev-parse …)`): Claude Code's safety check refuses it and only a person can approve it, every time. Leave scratch files in place and overwrite them, or delete by a literal path.
- `sharp` (realfavicon-mcp, via `image-adapter-node` and `check-favicon`) is a native dependency: keep it patched and review it on every bump. `node-html-parser` is declared as `^6.1.13`, the range `check-favicon` declares, and `bun.lock` locks it at 6.1.13.
